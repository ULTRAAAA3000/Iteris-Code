## 2. Как устроена проверка

В отличие от веб-проекта (`js-todo`, где проверки выполняются внутри страницы), здесь программа запускается на сервере через ту же песочницу, что и задания (Go Playground, Wandbox, [task-runtime.md](task-runtime.md)):

1. Берётся код пользователя (функции, типы, классы без `main`).
2. К нему дописывается скрытый **harness**: код, который вызывает функции пользователя с заранее известными данными и печатает для каждого требования `R1 PASS` или `R1 FAIL: причина`.
3. Сервер запускает собранную программу один раз и разбирает вывод: каждое требование получает свой зелёный или красный результат с подсказкой.

Правила сборки по языкам:
- **Python:** harness дописывается в конец `main.py`.
- **Java:** в `Main.java` лежат классы пользователя без `Main`, harness содержит `public class Main`. Заготовка начинается с `import java.util.*;`.
- **Go:** в заготовке уже есть блок `import` со всеми пакетами harness и строки вида `var _ = fmt.Sprint` («не удаляйте»), потому что импорты можно писать только в начале файла. В harness есть таймаут на случай взаимной блокировки горутин.

- **C++ (C++17, `g++`):** harness включает свои заголовки после кода пользователя, оборачивает проверки в `r("R1", [&] { … })` с помощью `eq` и `near`. Свойства классов проверяются поведением, а не текстом: `std::is_abstract` (абстрактный класс), пробный наследник со счётчиком деструкторов (виртуальный деструктор), SFINAE (`const`-методы). В заготовках заглушки компилируются вместе с harness; у классов без `const` и без `= 0` вимоги красные.
- **Pascal (Free Pascal 3.2):** harness содержит свои процедуры `IcEqInt` / `IcEqStr` / `IcEqBool` / `IcNear` / `IcDone` и основной блок `begin … end.`; код пользователя заканчивается последней подпрограммой, без основного блока. Перехватить вывод процедуры нельзя, поэтому ТЗ возвращают значения (строки, числа), а не печатают. **Внимание:** в режиме по умолчанию тип `integer` 16-битный (до 32767), все числа в тестах держим в этих пределах.
- **HTML:** это веб-проект, а не программа на сервере: формат `Project` из `src/projects/types.ts`, требования проверяет тот же рушій `src/projects/sandbox.ts` внутри страницы в iframe (`sandbox="allow-scripts"`), что и у `js-todo`. Требования записаны декларативно (`selector`, `text`, `attr`, `count`, `not`, `source`) и превращаются в JS-проверки функцией `pageChecksToJs` (`content/projects-draft/page-checks.ts`). Страница пользователя может вообще не содержать JavaScript.

Harness не читает ввод, файлы и сеть, детерминирован, всегда завершается с кодом 0.

## 3. Как проверено

Тест `tests/projects-draft.test.mjs` по-настоящему запускает все проекты локальными `python3`, `javac`/`java` и `go` (если инструмента нет, язык пропускается):
- эталонное решение проходит все требования, код завершения 0;
- заготовка компилируется, а каждое требование в ней красное;
- в harness нет чтения ввода, файлов и сети.

Для Python, Java и Go дополнительно по каждому проекту вручную проверена одна «неправильная» реализация (ошибка на единицу, не тот порядок и т. п.): хотя бы одно требование краснеет. 30 проверок проходят.

Для **C++, Pascal и HTML** проверка строже: в `tests/projects-draft/mutations-<язык>.mjs` для каждого проекта описаны «поломки» эталона (`replace` + список требований, которые должны покраснеть), и тест требует, чтобы **каждое требование имело хотя бы одну поломку, которая его краснит**. Так видно, что проверки настоящие, а не «всегда зелёные». Примеры ловушек, найденных этим способом: у треугольника 3-4-5 множитель `(s − c)` равен 1, поэтому его удаление ничего не ломает; `integer` в Free Pascal 16-битный; для `harness` нельзя ставить `override` на пробный класс (иначе «поломка» не компилируется).

- C++: `node tests/projects-draft.test.mjs cpp` (13 проверок), нужен `g++`.
- Pascal: `node tests/projects-draft.test.mjs pascal` (13 проверок), нужен `fpc` (`apt-get install fp-compiler`).
- HTML: `node tests/projects-draft-web.test.mjs` (8 проверок), нужен `jsdom`; входит в `npm test`. Дополнительно сверено в реальном Chromium (iframe с `sandbox="allow-scripts"`, как на сайте): эталоны 100%, заготовки почти 0%, все поломки краснят свои требования.

Поменять мутации или добавить их для Python, Java, Go можно, положив файл `mutations-<язык>.mjs`: тест подхватит его сам.

## 4. Что нужно для публикации

1. Дописать курсы (Go до 110 уроков, остальные по шаблону) и уточнить номера уроков в поле `lesson`.
2. Добавить тип проекта с запуском на сервере: `/api/project-run` (или расширить `/api/run`) принимает код, собирает его с harness (harness остаётся на сервере и не уходит в браузер, как и проверки `js-todo`), запускает и возвращает вердикты R1–Rn. Лимиты и учёт XP как у `/api/run` и `/api/progress/complete`.
3. Интерфейс: страница проекта с ТЗ, контрактом, редактором и отчётом по требованиям (существующая страница `js-todo` показывает ту же структуру).
4. Подключить `content/projects-draft/<язык>.ts` в `lib/content.ts` и перенести черновики в рабочую папку. HTML-проекты (`content/projects-draft/html.ts`) уже в формате `Project`, им новый тип не нужен: достаточно вставить их в `PROJECTS` (`content/projects/index.ts`) и положить решения в `tests/solutions/`.
5. Прочитать ТЗ глазами новичка и при необходимости упростить; проверить фактическую точность формулировок.

## 5. Как добавить или поправить проект

Тип: `content/projects-draft/types.ts`. Проекты: `content/projects-draft/<язык>.ts`, эталоны: `tests/projects-draft/solutions-<язык>.mjs`, поломки: `tests/projects-draft/mutations-<язык>.mjs`. После правки запустить `node tests/projects-draft.test.mjs <python|java|go|cpp|pascal>` (для HTML: `node tests/projects-draft-web.test.mjs`).

Практические советы, добытые на C++, Pascal и HTML:
- Заготовка должна компилироваться вместе с harness, а требования в ней быть красными: пишите заглушки с «неправильным» результатом (`-1`, `true`, пустая строка), а не просто пустые.
- Не упоминайте в комментариях слова, которые ищут проверки по тексту кода.
- Проверяйте поведение, а не текст: `std::is_abstract`, счётчик деструкторов, SFINAE вместо поиска слов `virtual` и `const` регулярным выражением.
- Каждое требование должно иметь поломку, которая его краснит (см. выше), и граничные случаи (пустой ввод, равенство границе, один элемент).
