# Практические задания: как они запускаются и проверяются

> Этот документ описывает **единый метод**, по которому на платформе работают практические задания «пиши код в редакторе, запускай, смотри результат, получай проверку и анимацию успеха».
> Метод отработан на Go (11 заданий, по одному на урок). **По тому же шаблону добавляются все остальные языки**, смотри раздел 6.
> Порядок этапов: [main-plan.md](main-plan.md). Описание продукта: [about.md](about.md).
> Последнее обновление: 15.11.2026.

## 1. Идея в одной схеме

```
Урок (теория)  +  Задание (редактор, терминал, кнопка «Запустить»)
                         │
        ┌────────────────┴─────────────────┐
   runtime: "js"                      runtime: "remote"
   Web Worker в браузере              сервер запускает код в «песочнице» языка
   tests (как Vitest)                 и сам сверяет результат со списком checks
        │                                   │
        └────────────── одинаковый результат: results + error ──────────────┐
                                                                             ▼
                          терминал: вывод программы, ✓/✗ по каждой проверке, «Пройдено N из M»
                          успех: анимация, +XP, серия (для вошедшего пользователя)
```

- **JS** выполняется прямо в браузере (Web Worker, тесты в стиле Vitest). Так было до сих пор.
- **Все остальные языки** (Go, Python, Java, C++, PHP, Pascal, …) в браузере нормально не запускаются, поэтому код отправляется на наш сервер (`POST /api/run`), тот запускает его во внешней «песочнице» и проверяет результат. Метод **одинаков для любого языка**: меняется только маленький адаптер песочницы.

## 2. Что где лежит

## 3. Как устроено задание (`RemoteTask`)

```ts
{
  ...base,                       // course, runtime: "remote", lang, file, editorLang, premium
  id: "go-sum-product",          // уникальный id (дальше он попадает в базу)
  lesson: "go/4",                // к какому уроку привязано: одно задание на урок
  xp: 20,
  title, context, brief: [...],  // заголовок, «зачем это в работе», постановка (HTML-абзацы)
  starter: `package main ...`,   // заготовка кода в редакторе
  checks: [ ... ],               // как проверяем (см. ниже)
}
```

### Проверки (`checks`): одинаковы для всех языков

Каждая проверка — одна строка в терминале (`✓` или `✗`). Заполняется **ровно одно** из `equals` / `has` / `matches`.

| Поле | Значение |
|---|---|
| `on` | `"stdout"` — вывод программы, `"source"` — исходный код пользователя |
| `name` | Что видит пользователь: «Сумма и произведение: 13 и 42» |
| `equals` | Точное совпадение (для stdout пробелы в конце строк и пустые строки в конце не учитываются) |
| `has` | Содержит подстроку (удобно для многострочных кусков: `"a\nb"`) |
| `matches` | Регулярное выражение (строкой, с двойным экранированием: `"\\bfor\\b"`) |
| `not` | Инвертировать (например, «в выводе нет FAIL») |
| `hint` | Подсказка, если не прошло |

Для `equals` по stdout терминал сам показывает «ожидалось / получено».

### Как писать хорошее задание

1. **Заготовка уже запускается или даёт понятную ошибку компилятора.** Ошибка компиляции в терминале — тоже обучение (например, `price*qty` с разными типами в уроке 3).
2. **`main` пишем сами и оставляем закрытым**, пользователь дописывает функцию, тип или метод. Так вывод предсказуем и проверяется без скрытых тестов.
3. **Проверок минимум три**: несколько частных (`has`) + одна общая (`equals`) + при необходимости `source`, если нужно потребовать конструкцию урока (`for`, `defer`, метод с указателем).
4. **Заготовка не должна проходить все проверки.** Это проверяет тест.
5. Текст на украинском (как весь интерфейс), код в заготовке без «подсказок-решений».

## 4. Как работает запуск

1. Пользователь нажимает «▶ Запустить» (или Ctrl+Enter). Клиент шлёт `POST /api/run { taskId, code }`.
2. Сервер проверяет Origin (CSRF), задание (`runtime: "remote"`), размер кода, **лимит запусков** (12 в минуту на аккаунт, для гостя на IP; таблица `auth_throttle`).
3. Адаптер языка из `RUNNERS` запускает код и возвращает `{ stdout, stderr, error?, timedOut?, exitCode? }`.
4. `evalChecks` сравнивает результат с `checks`. Аварийное завершение (panic, исключение) всегда считается провалом.
5. Ответ: `{ passed, results[], stdout, error?, proof? }`. Если всё пройдено и пользователь вошёл, добавляется `proof`.
6. Терминал показывает «Вывод программы» и результаты проверок; рядки появляются по очереди. При успехе: зелёное свечение терминала, карточка «Завдання розв'язано!» с конфетти, затем сохранение результата.

**Защита от подделки.** `POST /api/progress/complete` для remote-заданий не верит флагу `passed` из браузера: нужен `proof`, подписанный сервером (HMAC, привязан к пользователю, заданию и точному коду, живёт 15 минут). Награды выдаются один раз за задание (уникальность в `xp_events`).

## 5. Как это выглядит для Go

Песочница: **Go Playground** (`https://go.dev/_/compile`), бесплатный официальный сервис. Адаптер `goPlayground` в `lib/runners.ts`:

- отправляет один файл `package main` формой `version=2&body=...&withVet=false`;
- собирает `stdout` и `stderr` из событий, ошибки компиляции получает как текст (имя файла заменяется на `main.go`);
- распознаёт тайм-аут и аварийный код завершения.

Особенности Go Playground, которые учтены в заданиях:

- **нет сети**: сервер из урока 10 не запускается, поэтому обработчик вызывается напрямую через `net/http/httptest`;
- **нет ввода (stdin)**: задания ничего не читают с клавиатуры;
- **один файл**: нельзя положить рядом пакет и `_test.go`, поэтому урок 11 учит табличному тесту «вручную» (цикл по таблице и вывод `ok`/`FAIL`);
- в песочнице фиксированное «время», `time.Now()` и случайные числа в заданиях лучше не использовать.

## 6. Как добавить другой язык (чеклист)

Пример: **Python**.

1. **Выбрать песочницу** для языка (см. таблицу ниже) и проверить её условия: лимиты, время жизни, стоимость, нужен ли ключ.
2. **Типы.** В `src/tasks/types.ts` добавить язык в `RemoteLang`: `"go" | "python"`.
3. **Адаптер.** В `lib/runners.ts` написать объект `RemoteRunner` (по образцу `goPlayground`): метод `run(code)` отправляет код и возвращает `{ stdout, stderr, error?, timedOut?, exitCode? }`; добавить его в `RUNNERS`. Если нужен секретный ключ, добавить поле в `lib/env.ts` и раздел в `SETUP.md`.
4. **Задания.** Создать `content/tasks/python.ts` по образцу `go.ts` (`base` с `lang: "python"`, `file: "main.py"`, `editorLang: "python"`), по одному заданию на урок там, где материал позволяет (правило D13). Подключить в `src/tasks/index.ts`: `...PYTHON_TASKS`.
5. **Эталоны.** Добавить решения в `tests/solutions.mjs` (id задания → полный код).
6. **Тест запуска.** Скопировать `tests/go-tasks.test.mjs` в `tests/python-tasks.test.mjs`: заменить команду запуска на `python3` (проверка эталонов и заготовок реальным интерпретатором). Добавить в `package.json`.
7. **Проверить мобильную версию** (360, 390, 414 px) и прогнать `npm run check`, `npm test`, `npm run test:ui`.
8. **Обновить документацию**: этот файл (таблица языков ниже), `main-plan.md`, `about.md`.

Интерфейс (редактор, терминал, анимация, сохранение результата, лимиты, подпись) менять **не нужно**: он общий.

### Кандидаты для остальных языков

Условия сервисов меняются, перед подключением их нужно проверить заново.

| Язык | Как запускать | Заметки |
|---|---|---|
| Go | Go Playground через сервер | ✅ сделано |
| Python, SQL | WebAssembly в браузере (Pyodide, sql.js) | без сервера, но отдельная работа: новый тип `runtime`, который выполняется в Worker |
| HTML, CSS, JS-проекты | `iframe sandbox` и проверка DOM | этап 3 плана |
| Java, C++, PHP, Pascal, Bash | серверная песочница с несколькими языками (например, самостоятельно размещённый Piston или публичный сервис вроде Wandbox) | подключается тем же `RemoteRunner`; публичные сервисы могут быть с ограничениями, свой сервер даёт стабильность за деньги |
| TypeScript | как JS после транспиляции или WebAssembly | отдельное решение |

## 7. Известные ограничения

- **Внешняя зависимость.** Если go.dev недоступен или ограничивает запросы, пользователь видит «Сервіс запуску тимчасово недоступний». Запасной вариант на будущее: свой сервер запуска (вопрос Q6 в `main-plan.md`).
- **Задержка.** Запуск занимает от доли секунды до нескольких секунд (сеть + компиляция). В терминале показывается «Код надіслано на сервер…».
- **Проверка по выводу.** Пользователь может «обмануть» задание, напечатав готовый ответ. Для обучения это допустимо (XP даётся один раз). Для заданий, где это критично, добавляйте `source`-проверки на нужную конструкцию. Скрытые тесты (вторым файлом) возможны для языков, где песочница принимает несколько файлов; это дополнение пока не сделано.
- **Гость** может запускать код (лимит по IP), но результат не сохраняется и XP не получает.
