# Практические задания: как они запускаются и проверяются

> Этот документ описывает **единый метод**, по которому на платформе работают практические задания «пиши код в редакторе, запускай, смотри результат, получай проверку и анимацию успеха».
> Метод отработан на Go, затем применён к Python, Java, C++, PHP, Pascal и TypeScript (по одному заданию на урок, где материал позволяет). **По тому же шаблону добавляются остальные языки**, смотри раздел 6.
> Порядок этапов: [main-plan.md](main-plan.md). Описание продукта: [about.md](about.md).
> Последнее обновление: 15.11.2026.

## 1. Идея в одной схеме

```
Урок (теория)  +  Задание (редактор, терминал, кнопка «Запустить»)
                         │
        ┌────────────────┴─────────────────┐
   runtime: "js"                      runtime: "remote"
   Web Worker в браузере              сервер запускает код в «песочнице» языка
   tests (как Vitest)                 и сам сверяет результат со списком checks
        │                                   │
        └────────────── одинаковый результат: results + error ──────────────┐
                                                                             ▼
                          терминал: вывод программы, ✓/✗ по каждой проверке, «Пройдено N из M»
                          успех: анимация, +XP, серия (для вошедшего пользователя)
```

- **JS** выполняется прямо в браузере (Web Worker, тесты в стиле Vitest). Так было до сих пор.
- **Все остальные языки** (Go, Python, Java, C++, PHP, Pascal, …) в браузере нормально не запускаются, поэтому код отправляется на наш сервер (`POST /api/run`), тот запускает его во внешней «песочнице» и проверяет результат. Метод **одинаков для любого языка**: меняется только маленький адаптер песочницы.

## 3. Как устроено задание (`RemoteTask`)

```ts
{
  ...base,                       // course, runtime: "remote", lang, file, editorLang, premium
  id: "go-sum-product",          // уникальный id (дальше он попадает в базу)
  lesson: "go/4",                // к какому уроку привязано: одно задание на урок
  xp: 20,
  title, context, brief: [...],  // заголовок, «зачем это в работе», постановка (HTML-абзацы)
  starter: `package main ...`,   // заготовка кода в редакторе
  checks: [ ... ],               // как проверяем (см. ниже)
}
```

### Проверки (`checks`): одинаковы для всех языков

Каждая проверка — одна строка в терминале (`✓` или `✗`). Заполняется **ровно одно** из `equals` / `has` / `matches`.

| Поле | Значение |
|---|---|
| `on` | `"stdout"` — вывод программы, `"source"` — исходный код пользователя |
| `name` | Что видит пользователь: «Сумма и произведение: 13 и 42» |
| `equals` | Точное совпадение (для stdout пробелы в конце строк и пустые строки в конце не учитываются) |
| `has` | Содержит подстроку (удобно для многострочных кусков: `"a\nb"`) |
| `matches` | Регулярное выражение (строкой, с двойным экранированием: `"\\bfor\\b"`) |
| `not` | Инвертировать (например, «в выводе нет FAIL») |
| `hint` | Подсказка, если не прошло |

Для `equals` по stdout терминал сам показывает «ожидалось / получено».

### Как писать хорошее задание

1. **Заготовка уже запускается или даёт понятную ошибку компилятора.** Ошибка компиляции в терминале — тоже обучение (например, `price*qty` с разными типами в уроке 3).
2. **`main` пишем сами и оставляем закрытым**, пользователь дописывает функцию, тип или метод. Так вывод предсказуем и проверяется без скрытых тестов.
3. **Проверок минимум три**: несколько частных (`has`) + одна общая (`equals`) + при необходимости `source`, если нужно потребовать конструкцию урока (`for`, `defer`, метод с указателем).
4. **Заготовка не должна проходить все проверки.** Это проверяет тест.
5. Текст на украинском (как весь интерфейс), код в заготовке без «подсказок-решений».

## 4. Как работает запуск

1. Пользователь нажимает «▶ Запустить» (или Ctrl+Enter). Клиент шлёт `POST /api/run { taskId, code }`.
2. Сервер проверяет Origin (CSRF), задание (`runtime: "remote"`), размер кода, **лимит запусков** (12 в минуту на аккаунт, для гостя на IP; таблица `auth_throttle`).
3. Адаптер языка из `RUNNERS` запускает код и возвращает `{ stdout, stderr, error?, timedOut?, exitCode? }`.
4. `evalChecks` сравнивает результат с `checks`. Аварийное завершение (panic, исключение) всегда считается провалом.
5. Ответ: `{ passed, results[], stdout, error?, proof? }`. Если всё пройдено и пользователь вошёл, добавляется `proof`.
6. Терминал показывает «Вывод программы» и результаты проверок; рядки появляются по очереди. При успехе: зелёное свечение терминала, карточка «Завдання розв'язано!» с конфетти, затем сохранение результата.

**Защита от подделки.** `POST /api/progress/complete` для remote-заданий не верит флагу `passed` из браузера: нужен `proof`, подписанный сервером (HMAC, привязан к пользователю, заданию и точному коду, живёт 15 минут). Награды выдаются один раз за задание (уникальность в `xp_events`).

## 5. Песочницы по языкам

| Язык | Песочница | Адаптер |
|---|---|---|
| Go | Go Playground (`go.dev/_/compile`) | `goPlayground` в `lib/runners.ts` |
| Python, Java, C++, PHP, Pascal, TypeScript | Wandbox (`wandbox.org/api`), бесплатный, без ключа | `wandbox(язык, шаблон имени, файл)` в `lib/runners.ts` |

**Go Playground.** Отправляет один файл `package main` формой `version=2&body=...&withVet=false`, собирает `stdout` и `stderr` из событий, ошибки компиляции получает текстом.

**Wandbox.** Адаптер сам выбирает компилятор: берёт `GET /api/list.json` (кеш на час) и находит самую новую стабильную версию языка по шаблону имени (`cpython-3.*`, `openjdk-*`, `gcc-*`, `php-*`, `fpc-*`, без `head`). Версии в коде не зашиты, поэтому обновления на стороне сервиса ничего не ломают. Запрос: `POST /api/compile.json {compiler, code}`; из ответа берутся `program_output`, `program_error`, `compiler_error`, `status`. Ошибка компиляции распознаётся так: код завершения не нулевой, программа ничего не вывела, а компилятор написал текст. Предупреждения компилятора запуск не ломают. Во всех сообщениях `prog.*` заменяется на имя файла из редактора.

Почему Wandbox, а не Piston: публичный Piston с 15.02.2026 бесплатно недоступен (нужен токен, выдаётся только по запросу для учебных некоммерческих проектов).

### Особенности и правила по языкам

- **Нет сети и нет ввода (stdin).** Серверы, `requests`, чтение с клавиатуры в заданиях не используются. Вместо `input()` данные задаются в коде, вместо файлов на диске (Python) используется `io.StringIO`, вместо HTTP-сервера (Go) обработчик вызывается через `httptest`, форма PHP имитируется массивом.
- **Один файл.** Нельзя положить рядом пакет и `_test.go`, поэтому тесты (Go урок 11, Python урок 20) учат писать проверки внутри одной программы.
- **Java:** главный класс называется `Main` и идёт в файле первым, остальные классы после него; текст вывода только английский (ASCII), потому что кодировка stdout в Java зависит от настроек среды и кириллица может превратиться в `?`. Тест запускается с `LC_ALL=C` специально, чтобы это ловить.
- **Pascal:** длину строк с кириллицей не проверяем (это байты), строковые упражнения на латинице; клавиатуры нет, `readln` не используется.
- **C++:** стандарт C++17.
- **TypeScript:** компилятор проверяет типы, и ошибка типа показывается как ошибка компиляции (это часть обучения). Локальный тест компилирует с `--strict`; у Wandbox настройки компилятора по умолчанию могут быть мягче, поэтому у заданий всегда есть проверки вывода и кода, а не только «компилируется».
- **JavaScript** остаётся в браузере (Web Worker, тесты в стиле Vitest, `JsTask`). Функции, которым нужны `fetch` и `localStorage`, принимают их параметром, поэтому тестируются без сети.
- **Уроки без задания** перечислены в `NO_TASK` в `tests/remote-tasks.test.mjs` с причиной. Сейчас это PHP урок 8 (PDO): в песочнице нет базы данных, а расширение SQLite там не гарантировано.
- **Go:** фиксированное «время» в песочнице, `time.Now()` и случайные числа в заданиях лучше не использовать.

## 6. Как добавить другой язык (чеклист)

Пример: **Python**.

1. **Выбрать песочницу** для языка (см. таблицу ниже) и проверить её условия: лимиты, время жизни, стоимость, нужен ли ключ.
2. **Типы.** В `src/tasks/types.ts` добавить язык в `RemoteLang`: `"go" | "python"`.
3. **Адаптер.** В `lib/runners.ts` написать объект `RemoteRunner` (по образцу `goPlayground`): метод `run(code)` отправляет код и возвращает `{ stdout, stderr, error?, timedOut?, exitCode? }`; добавить его в `RUNNERS`. Если нужен секретный ключ, добавить поле в `lib/env.ts` и раздел в `SETUP.md`.
4. **Задания.** Создать `content/tasks/python.ts` по образцу `go.ts` (`base` с `lang: "python"`, `file: "main.py"`, `editorLang: "python"`), по одному заданию на урок там, где материал позволяет (правило D13). Подключить в `src/tasks/index.ts`: `...PYTHON_TASKS`.
5. **Эталоны.** Добавить решения в `tests/solutions/<язык>.mjs` (id задания → полный код) и подключить в `tests/solutions.mjs`.
6. **Тест запуска.** В `tests/remote-tasks.test.mjs` добавить язык в объект `LANGS`: имя файла, команда проверки наличия инструмента и функция запуска (компиляция и запуск локально). Тест сам проверит каждое задание: заготовка не проходит, эталон проходит все проверки.
7. **Проверить мобильную версию** (360, 390, 414 px) и прогнать `npm run check`, `npm test`, `npm run test:ui`.
8. **Обновить документацию**: этот файл (таблица языков ниже), `main-plan.md`, `about.md`.

Интерфейс (редактор, терминал, анимация, сохранение результата, лимиты, подпись) менять **не нужно**: он общий.

Условия сервисов меняются, перед подключением их нужно проверить заново.

| Язык | Как запускать | Заметки |
|---|---|---|

## 7. Известные ограничения

- **Живой сервис не проверен.** Адаптеры проверены на подставных ответах, а задания компиляторами и интерпретаторами локально. Реальный вызов `wandbox.org` и `go.dev` из среды разработки был недоступен, поэтому после деплоя нужно пройти по одному заданию на каждом языке вручную. Если формат ответа Wandbox (имена полей, названия компиляторов, требование к имени класса Java) отличается от ожидаемого, правится один адаптер.
- **Внешняя зависимость.** Если go.dev недоступен или ограничивает запросы, пользователь видит «Сервіс запуску тимчасово недоступний». Запасной вариант на будущее: свой сервер запуска (вопрос Q6 в `main-plan.md`).
- **Задержка.** Запуск занимает от доли секунды до нескольких секунд (сеть + компиляция). В терминале показывается «Код надіслано на сервер…».
- **Проверка по выводу.** Пользователь может «обмануть» задание, напечатав готовый ответ. Для обучения это допустимо (XP даётся один раз). Для заданий, где это критично, добавляйте `source`-проверки на нужную конструкцию. Скрытые тесты (вторым файлом) возможны для языков, где песочница принимает несколько файлов; это дополнение пока не сделано.
- **Гость** может запускать код (лимит по IP), но результат не сохраняется и XP не получает.

## 8. Практика HTML и CSS (`runtime: "page"`)

Для HTML и CSS нужен не терминал, а **страница с живым предпросмотром**. Работает целиком в браузере, без сервера.

**Как это устроено.**

- Слева теория, справа редактор (`index.html` или `style.css`), под ним предпросмотр страницы и терминал с результатами проверок. Предпросмотр обновляется через 0,3 секунды после паузы в наборе.
- Страница рисуется в `iframe` с `sandbox="allow-same-origin"`: **скрипты в нём не выполняются** (нет `allow-scripts`), поэтому код пользователя не может ничего сделать с нашим сайтом. Родитель читает DOM и стили iframe, потому что origin тот же.
- Кнопка «Перевірити» (Ctrl+Enter) прогоняет `PageCheck`-проверки по DOM и показывает те же ✓/✗, затем сохраняет результат так же, как для JS (проверка в браузере, без `proof`).
- Режимы: `edit: "html"` (пользователь пишет весь документ) и `edit: "css"` (готовая разметка `markup`, пользователь пишет только стили).

**Формат проверки (`PageCheck`).** Выбираются элементы по `selector`, отфильтровываются по `text` / `attr` / `style`, и оставшееся количество сравнивается с `count` (по умолчанию нужен хотя бы один). Все поля действуют вместе. Без `selector` проверяется только `source` (текст кода пользователя, `has` или `matches`). `not` инвертирует.

| Поле | Пример |
|---|---|
| `selector` | `"nav a.active"`, `"img:not([alt])"` |
| `count` | `3` (ровно), `{ min: 2 }`, `{ min: 1, max: 4 }` |
| `text` | `"Привіт, веб!"` (пробелы нормализуются) |
| `attr` | `{ name: "href", equals: "https://example.com" }` |
| `style` | `{ color: "#2e7d32", "padding-top": "16px" }` (вычисленные стили) |
| `source` | `{ matches: "grid-template-columns\\s*:\\s*repeat\\(\\s*3" }` |

**Правила хороших заданий HTML/CSS.**

1. **Цвета пишите в hex, длины в px**, и только полные свойства (`padding-top`, а не `padding`). Значения нормализуются (`#f00` и `rgb(255, 0, 0)` равны), но сокращённые свойства в разных браузерах вычисляются по-разному.
2. **Всё, что зависит от ширины экрана и темы, проверяйте по коду (`source`)**: сетку (`grid-template-columns` вычисляется в пиксели), медиазапросы, CSS-переменные в тёмной теме, `:hover`, псевдоэлементы. Иначе у человека с узким окном или тёмной системной темой проверка ложно упадёт.
3. Проверяйте результат, а не способ там, где способов несколько: в `style` через вычисленные значения, а `source` оставляйте для конструкций, которые и есть предмет урока (`@media`, `grid`, `var()`).
4. Для «в итоге не должно остаться» используйте `not: true` (например, `selector: "div", not: true` или `img:not([alt])`).
5. Заготовка не должна проходить все проверки, эталон обязан проходить все: это проверяет `tests/page-tasks.test.mjs` в jsdom.

**Ограничения.** jsdom не делает вёрстку, поэтому реальные размеры и позиции (`getBoundingClientRect`) проверить нельзя. В браузере то же самое можно, но тестов на живом браузере у нас нет: после деплоя нужно пройти по одному заданию HTML и CSS руками. Задания JavaScript про DOM и события (уроки 16 и 17) пока не сделаны: для них нужно выполнять код пользователя против страницы, а это требует отдельной безопасной песочницы (iframe с другого origin или DOM внутри воркера); `allow-scripts` вместе с `allow-same-origin` включать нельзя, так как такой iframe может снять с себя изоляцию.
