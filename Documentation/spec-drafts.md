## Навіщо
Проєкт за ТЗ (D10, етап 3) найкраще працює після повного курсу. Поки курси C++, Pascal і HTML дописуються (еталон: Go, 110 уроків, див. [go-course-authoring.md](go-course-authoring.md)), ТЗ пишуться наперед, у тому форматі, у якому вони підуть на сайт. Коли уроки будуть готові, чернетку або вставляють як є, або адаптують під нові уроки.

## Як влаштована чернетка
Файли: `content/drafts/{types,index,cpp,pascal,html}.ts`.

Чернетка (`SpecDraft`) це звичайне ТЗ: `context`, `brief`, `contract` (що має називатися так, а не інакше), `mockup` (приклад результату), `starter`, `xp`, `after` і `needs`, а також **вимоги R1…Rn**. Кожна вимога має:
- `short`: 8–80 символів звичайного тексту для терміналу;
- `text`: повне формулювання (HTML лише `<code>`, `<b>`, `<i>`);
- `hint`: наводить, але не видає рішення;
- `checks`: одна або кілька перевірок, **вимога виконана, коли пройшли всі**.

Перевірки це ті самі, що в звичайних завданнях: для C++ і Pascal `on: "stdout" | "source"` з `equals` / `has` / `matches` / `not`; для HTML `selector` / `text` / `attr` / `count` / `source`. Нового рушія не потрібно.

Чому не «рушій проєктів» з етапу 3A: він працює лише для веб-сторінок із JavaScript у iframe. C++ і Pascal запускаються на сервері (Wandbox), тому ТЗ для них стають звичайними `RemoteTask` з перевірками виводу, а HTML-ТЗ стають `PageTask`.

## Як опублікувати чернетку
1. Перенести або адаптувати текст під уроки, які тепер є в курсі (змінити `after`, за потреби й дані в `starter`/макеті).
2. Додати чернетку в `content/tasks/<курс>.ts` через `draftToTask(draft)` (перетворює вимоги на перевірки `R1.`, `R2.`… і вносить ТЗ у постановку) або скопіювати результат як звичайне завдання. Не забути про правила з [go-course-authoring.md](go-course-authoring.md) і [task-runtime.md](task-runtime.md): `main` для Pascal без `readln`, C++17, без `stdin`.
3. Перенести еталон і мутації з `tests/solutions/drafts-<курс>.mjs` у `tests/solutions/<курс>.mjs` (або лишити, якщо перевірку вважають окремим набором).
4. Прибрати чернетку з `content/drafts/` (щоб не було двох копій) і запустити `npm test` та `npm run test:ui`.

## Як писати нову чернетку
1. Описати її в `content/drafts/<курс>.ts` за зразком наявних.
2. Написати **еталонне рішення** й **мутації** в `tests/solutions/drafts-<курс>.mjs`. Мутація це заміна в еталоні (`replace: [[від, до]]`, або `[від, до, "all"]` для всіх входжень) і список вимог, що мають провалитися (`fails`).
3. Запустити `node tests/drafts.test.mjs`. Тест вимагає:
   - заготовка не проходить усе (або не компілюється);
   - еталон виконує **всі** вимоги, працює стабільно й завершується з кодом 0;
   - **кожна вимога має мутацію, що її ламає** (захист від «завжди зелених» перевірок);
   - тексти містять лише дозволені теги; вимог 6–10; XP 40–60; `after` існує в поточному плані;
   - чернетка ніде не підключена до сайту.
4. Практичні поради, винесені з цих дев'яти:
   - У заготовці не згадуйте в коментарях слова, які шукає перевірка джерела (`override`, `while`…), інакше заготовка «пройде» вимогу сама.
   - Для Pascal робіть регулярні вирази нечутливими до регістру (`ci("while")` у `content/drafts/pascal.ts`).
   - Не позначайте вимогу «пройденою» лише за наявності заглушки в заготовці: заготовку краще давати без тіл підпрограм.
   - Остання перевірка рядка в `stdout` може втратити кінцевий перенос: пишіть `(?:\n|$)`.
   - Вихід із вимогою «останній рядок виводу» перевіряйте через `matches`, а повний збіг лишайте окремою вимогою `equals`.
   - Мутація має справді змінювати результат: у трикутника 3-4-5 множник `(s − c)` дорівнює 1, тож його видалення нічого не ламає.

## Запуск тесту
```
npm i --no-save jsdom        # для HTML-чернеток
node tests/drafts.test.mjs   # потрібні g++ (C++) і fpc (Pascal); якщо інструмента немає, запуск курсу пропускається
```
У Ubuntu: `apt-get install g++ fp-compiler`.
