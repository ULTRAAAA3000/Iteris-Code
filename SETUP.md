# Настройка аккаунтов и личного кабинета (Cloudflare Pages + D1 + Google OAuth)

Код уже в репозитории. Чтобы вход и кабинет заработали на `iteris-code.pages.dev`, нужно один раз настроить три вещи.

## 1. Google OAuth
1. Откройте [Google Cloud Console](https://console.cloud.google.com/) → создайте проект → **APIs & Services → OAuth consent screen** (тип External, scopes: `openid`, `email`, `profile`).
2. **Credentials → Create credentials → OAuth client ID → Web application**.
3. В **Authorized redirect URIs** добавьте адреса сайта **точно с косой чертой в конце**:
   - `https://iteris-code.pages.dev/`
   - `http://localhost:8788/` (для локальной разработки)
   - свой домен, когда подключите его (`https://ваш-домен/`)
4. Сохраните **Client ID** и **Client secret**.

## 1б. GitHub OAuth (необязательно)
Кнопка «Увійти через GitHub» появляется на страницах входа и регистрации, только когда заданы обе переменные ниже.
1. GitHub → **Settings → Developer settings → OAuth Apps → New OAuth App**.
2. **Authorization callback URL**: адрес сайта с косой чертой в конце, например `https://iteris-code.pages.dev/` (как и для Google, это главная страница).
3. Сохраните **Client ID** и создайте **Client secret**.
4. В Cloudflare Pages → Settings → Variables and Secrets добавьте `GITHUB_CLIENT_ID` (обычная) и `GITHUB_CLIENT_SECRET` (**Secret**), затем сделайте новый деплой.
5. Проверка: `/api/auth/health` покажет `features.github: true`.

Если у человека уже есть аккаунт с той же подтверждённой почтой (Google или по паролю), GitHub привяжется к нему, а не создаст второй. Берётся основная подтверждённая почта GitHub; без неё вход отклоняется.

## 1в. Свой домен и кабинет на поддомене (iteris-code.org + dashboard.iteris-code.org)

Сайт открывается на основном домене, личный кабинет на `dashboard.iteris-code.org`. Это один и тот же проект Cloudflare Pages с двумя доменами, отдельного деплоя не нужно.

1. Cloudflare Pages → проект → **Custom domains → Set up a custom domain**: добавьте `iteris-code.org`, затем `dashboard.iteris-code.org` (и при желании `www.iteris-code.org`). Если домен в Cloudflare DNS, записи CNAME создадутся сами; иначе добавьте CNAME на `<проект>.pages.dev` у регистратора.
2. **Variables and Secrets** → `SITE_URL` = `https://iteris-code.org` (canonical, Open Graph, sitemap).
3. В Google и GitHub OAuth добавьте адрес основного домена с косой чертой: `https://iteris-code.org/`. Вход всегда происходит на основном домене (на кабинете кнопка «Увійти» ведёт туда). Адрес `pages.dev` можно оставить.
4. Новый деплой.

Как это работает:
- Cookie сессии ставится с `Domain=.iteris-code.org`, поэтому вход на основном домене действует и на кабинете. Старая cookie, привязанная только к хосту, при входе и выходе стирается автоматически. Эти пользователи просто войдут заново один раз.
- `iteris-code.org/dashboard` (закладки, письма, адрес возврата после оплаты) автоматически переносит на `dashboard.iteris-code.org`. На кабинете главная страница `/` и есть кабинет, любая другая страница (включая логотип) ведёт на основной домен.
- На `pages.dev`, `localhost` и превью-адресах ничего не меняется: кабинет остаётся на `/dashboard`.
- Другой домен или название поддомена: переменные сборки `ROOT_DOMAIN` (по умолчанию `iteris-code.org`) и `DASH_SUBDOMAIN` (по умолчанию `dashboard`) в Cloudflare Pages, а для cookie `COOKIE_DOMAIN`. Все три задавайте согласованно.
- Адрес возврата после оплаты можно указать как `https://dashboard.iteris-code.org/`.

## 3. Cloudflare Pages
В проекте Pages → **Settings**:
- **Functions → D1 database bindings**: имя переменной `DB`, база `iteris-code` (для Production и Preview).
- **Variables and Secrets** (Production и Preview):
  - `GOOGLE_CLIENT_ID` (обычная переменная)
  - `GOOGLE_CLIENT_SECRET` (**Secret**)
  - `SESSION_SECRET` (**Secret**, случайная строка: `openssl rand -base64 48`)
  - `SITE_URL` (обычная переменная, необязательная): адрес сайта без косой черты, например `https://iteris-code.pages.dev` или ваш домен. Он попадает в `canonical`, Open Graph и `sitemap.xml`. Без неё берётся `https://iteris-code.pages.dev`.
- **Build command** `npm run build`, **Build output directory** `dist` (рекомендуется). Если там стоит `/`, сайт тоже заработает: при сборке в Cloudflare готовые файлы дублируются в корень. Папка `functions/` подхватывается автоматически.

После этого сделайте новый деплой. Кнопка «Увійти» в шапке должна открывать окно Google.

## 4. Оплата Pro (Lemon Squeezy)
Подписка $5/месяц оформляется через [Lemon Squeezy](https://www.lemonsqueezy.com/) (он выступает продавцом и сам собирает налоги). Начните с **Test mode**.

1. Создайте магазин и товар **Iteris Pro** с типом *Subscription*, цена $5 в месяц.
2. **Ссылка на оплату**: у товара нажмите *Share* и скопируйте ссылку вида `https://<магазин>.lemonsqueezy.com/checkout/buy/<id>`. Это значение `LEMONSQUEEZY_CHECKOUT_URL`.
3. **Вебхук**: *Settings → Webhooks → +*:
   - URL: `https://iteris-code.pages.dev/api/webhooks/payment`
   - придумайте **Signing secret** (длинная случайная строка) и сохраните его как `LEMONSQUEEZY_WEBHOOK_SECRET` (**Secret**);
   - события: `subscription_created`, `subscription_updated`, `subscription_cancelled`, `subscription_resumed`, `subscription_expired`, `subscription_paused`, `subscription_unpaused` (остальные сайт всё равно игнорирует).
4. По желанию `LEMONSQUEEZY_VARIANT_ID`: ID варианта товара. Тогда сайт принимает события только для него.
5. В настройках товара укажите адрес возврата после оплаты: `https://iteris-code.pages.dev/dashboard`.
6. Если база уже создана, один раз выполните миграцию (для новой базы достаточно `schema.sql`):
   ```bash
   npx wrangler d1 execute iteris-code --remote --file=migrations/0002_payments.sql
   ```
7. Новый деплой. Проверка в Test mode: «Перейти на Pro за $5» → тестовая карта `4242 4242 4242 4242` → в кабинете должен появиться бейдж Pro (если нет, нажмите «Оновити статус»).

Как это работает: `user_id` передаётся в оплату как `checkout[custom][user_id]` и возвращается в вебхуке, поэтому отдельная таблица клиентов не нужна. Подпись вебхука (HMAC-SHA256) проверяется на сервере. Дубли доставки игнорируются (таблица `payment_events`), запоздавшие старые события тоже. После `subscription_cancelled` доступ сохраняется до конца оплаченного периода, при неудачном платеже действует льготный период 3 дня.

> Перед запуском проверьте, что Lemon Squeezy выплачивает деньги в вашу страну, и посмотрите актуальные тарифы: фиксированная часть комиссии на платеже в $5 заметна. Другую платёжку (Stripe, Monobank) можно подключить по аналогии, логика лежит в `lib/billing.ts` и `functions/api/webhooks/`.

## 5. Вход по почте и паролю (Turnstile + Resend)
Форма входа по почте и паролю есть всегда, ничего настраивать для неё не нужно (кроме `SESSION_SECRET` и миграции ниже). Всё остальное появляется само, как только вы зададите переменные в Cloudflare Pages и сделаете новый деплой:

| Что задать | Что появится |
|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | кнопка «Увійти через Google» (без них её просто нет) |
| `TURNSTILE_SITE_KEY` + `TURNSTILE_SECRET_KEY` (нужны **оба**) | антибот-виджет Cloudflare Turnstile на всех формах (без них форм без капчи, но с лимитами попыток) |
| `RESEND_API_KEY` + `MAIL_FROM` (нужны **оба**) | письма: подтверждение почты и «Забули пароль» (без них ссылки «Забули пароль» нет, а регистрация сразу открывает кабинет) |

1. **Turnstile**: Cloudflare Dashboard → *Turnstile* → *Add widget*, домен сайта (и `localhost` для разработки), режим *Managed*. **Site key** кладётся в `TURNSTILE_SITE_KEY` (обычная переменная), **Secret key** в `TURNSTILE_SECRET_KEY` (**Secret**).
2. **Письма (Resend)**: на [resend.com](https://resend.com) подтвердите домен (DNS-записи), создайте API-ключ. `RESEND_API_KEY` это **Secret**, `MAIL_FROM` обычная переменная, например `Iteris Code <noreply@ваш-домен>`.
3. Таблицы и колонки в базе создаются и дополняются автоматически при первом запросе к API (`lib/schema.ts`), вручную выполнять `migrations/0003_password_auth.sql` не нужно. Файл оставлен как справка.
4. Новый деплой (переменные применяются только после него).

### Если вход или регистрация пишут «Помилка сервера»
1. Откройте в браузере `https://ваш-сайт/api/auth/health`. Ответ `{"ok":true,...}` значит, что настройки в порядке. Иначе в `problems` написано, чего не хватает (например, `SESSION_SECRET`).
2. Добавьте `?hash=1` (`/api/auth/health?hash=1`), чтобы проверить, укладывается ли хеширование пароля в лимит процессорного времени воркера. Если вместо JSON появляется страница Cloudflare «Error 1102», нужен платный план Workers либо меньше итераций хеша.
3. Сообщение на форме содержит код, например `Помилка сервера (код 500, db_schema)`. Коды: `db_schema` (нет таблицы или колонки; после деплоя исправляется само), `db_error` (ошибка базы), `db_binding_missing` (к проекту не привязана D1 с именем `DB`), `server_error` (остальное; подробности в логах: Cloudflare → Workers & Pages → проект → Logs).
4. Переменные окружения применяются только после нового деплоя (Deployments → Retry deployment).

Как это устроено:
- **Пароль** хешируется на сервере алгоритмом PBKDF2-SHA256 (100 000 итераций, уникальная соль на каждый пароль; это максимум, который разрешают Cloudflare Workers). В базе лежит только хеш, сам пароль нигде не сохраняется и не логируется. Длина пароля 8–128 символов.
- **Подтверждение почты** (когда настроены письма): после регистрации уходит письмо со ссылкой (24 часа). Войти по паролю можно только после подтверждения. Повторная регистрация до подтверждения присылает новое письмо. Если письма не настроены, регистрация сразу открывает кабинет, а когда вы их включите, такие аккаунты подтверждают адрес через «Забули пароль».
- **Забыли пароль**: ссылка из письма действует 1 час и срабатывает один раз. Ответ сервера одинаков для любой почты, поэтому нельзя выяснить, зарегистрирован ли адрес. Сброс по ссылке заодно подтверждает почту.
- **Токены из писем** в базе хранятся только как SHA-256, сами ссылки лежат в хеш-части адреса (`/#/reset/…`), поэтому не попадают в логи серверов.
- **Лимиты попыток** (таблица `auth_throttle`): 10 неудачных входов на почту за 15 минут, 5 писем на почту в час, плюс лимиты по IP.
- **Google с той же почтой**: если акаунт с такой почтой уже есть, Google привязывается к нему. Пароль непроверенного акаунта при этом сбрасывается (его мог создать не владелец почты).

Тестовые ключи Turnstile для локальной разработки (всегда проходят проверку): site key `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`.

## Разработка на TypeScript
Весь код на TypeScript со строгими типами (`strict`, `erasableSyntaxOnly`):

| Папка | Что внутри |
|---|---|
| `src/` | фронтенд: `main.ts` (роутер), `views.ts`, `auth.ts` (вход и кабинет), `login.ts` (формы входа по почте), `workspace.ts` + `editor.ts` (экран задания), `runner/` (запуск тестов в Web Worker), `tasks/` (практические задания) |
| `src/data/reference/` | публичный справочник по языкам (виден без входа) |
| `content/` | **закрытый контент**: `lessons.js` (тексты уроков, типы в `lessons.d.ts`) и `tasks/` (задания). В сборку для браузера не входит, отдаётся только вошедшему через `/api/courses` и `/api/lesson` |
| `functions/`, `lib/` | Cloudflare Pages Functions (API) и общие помощники |
| `tests/` | автотесты |

Команды:
```bash
npm install                 # один раз
npm run check               # проверка типов (фронтенд + Functions)
npm run build               # сборка в dist/ (esbuild): app.js, runner.worker.js, index.html
npm test                    # тесты API, входа по паролю и раннера (Node 22.18+)
npm i --no-save jsdom && npm run test:ui    # тесты интерфейса (нужна предварительная сборка)
```
Cloudflare Pages сам выполнит `npm install` и `npm run build`; версия Node берётся из `.node-version`.

## Факты в кабинете
Плашка «Цікавий факт» (раз в 5 часов, про язык, выбранный на онбординге) берёт тексты из `content/facts.ts`. Это закрытый контент: в браузер попадает только один выбранный сервером факт через `GET /api/dashboard`.
- Формат: для каждого курса (ключи как в `content/lessons.js`) и для `general` два списка: `f` (факты) и `t` (подсказки). После каждых трёх фактов показывается одна подсказка.
- Чтобы добавить запись, допишите строку в нужный список. Никаких счётчиков и номеров обновлять не нужно: цикл сам подстроится под новую длину.
- Правила для текста: 20–300 символов, без дубликатов среди всех записей, код оформляйте обратными кавычками (`так`), HTML-теги вне кавычек не нужны (текст экранируется). Утверждения должны быть правдивыми и проверяемыми: сомнительные факты лучше не добавлять.
- `npm test` проверяет, что для каждого курса не меньше 20 фактов и 7 подсказок, а все тексты уникальны и корректно оформлены.

## Практические задания
Задания лежат в `content/tasks/index.ts`: условие, бизнес-контекст, заготовка кода, тесты (API как у Vitest: `describe`, `it`, `expect`) и флаг `premium`. Чтобы добавить задание:
1. Описать его в `TASKS` и привязать к уроку (`lesson: "js/8"`).
2. Добавить эталонное решение в `tests/solutions.mjs` (в сборку оно не попадает).
3. Запустить `npm test`: он проверяет, что заготовка **не** проходит тесты, а эталон проходит все.

Как работает проверка: код пользователя и тесты запускаются в отдельном Web Worker (без доступа к DOM, сеть отключена, жёсткий тайм-аут 4 с против бесконечных циклов). Pro-задания проверяются **и на клиенте** (кнопка заблокирована), **и на сервере** (`/api/progress/complete` отвечает 402 без активной подписки).

## Проекты по ТЗ
Проект (ТЗ, вимоги с автопроверкой, заготовка) лежит в `content/projects/index.ts`, как и задания: это закрытый контент, он отдаётся только вошедшему через `GET /api/project?id=…`. Чтобы добавить проект:
1. Описать его в `PROJECTS` по образцу `js-todo`: `id`, `lesson` (после какого урока предлагается, например `"js/17"`), `course`, `title`, `context`, `brief`, `contract` (id и классы, на которые опираются проверки), `mockup`, `starter` (один файл `index.html` с HTML, CSS и JS), `xp`, `premium`.
2. Вимоги `R1…Rn` идут подряд. У каждой есть `text`, `hint` и `check`: тело async-функции, которая выполняется внутри страницы пользователя и возвращает `true` или строку с объяснением. Помощники: `$`, `$$`, `text`, `css`, `click`, `type`, `press`, `wait`. Вимоги должны работать независимо друг от друга: каждая добавляет свои данные и ищет именно их. В тексте `check` не используйте обратные кавычки и `${}` без необходимости (строка лежит в шаблонном литерале).
3. Добавить эталонное решение в `tests/solutions.mjs` (`PROJECT_SOLUTIONS`, в сборку не попадает) и запустить `npm test` и `npm run test:ui`: заготовка не должна выполнять все вимоги, эталон обязан выполнять все.
4. Пометка проекта у урока, карточка в конце урока, чип на пути и запись в кабинете появляются автоматически. XP начисляется один раз (`taskId` = id проекта), лимит кода 60000 символов.

Как работает проверка: страница пользователя запускается в `iframe` с `sandbox="allow-scripts"` (без `allow-same-origin`), к ней дописывается скрипт, который выполняет вимоги и присылает звіт через `postMessage` с одноразовым кодом. Как и для заданий, проверка выполняется в браузере и технически обходима.

## Как это устроено

- Сессия: подписанная HMAC-SHA256 cookie `session` (`HttpOnly; Secure; SameSite=Lax`, 30 дней), таблицы сессий не нужны.
- `lesson_id` в `user_progress` имеет вид `python/3` (курс/номер урока).
- Стрик считается по **UTC**-датам и растёт, когда пользователь отмечает урок пройденным или решает практическое задание. Первичная синхронизация локального прогресса после входа стрик не увеличивает.
- POST-запросы проверяют заголовок `Origin` (защита от CSRF).

## Ограничения и что ещё не сделано
- **Оплата**: реализован Lemon Squeezy (см. раздел 4); не проверена на реальной платёжке: проверьте в Test mode.
- Автопроверка выполняется в браузере, поэтому технически её можно обойти (подделать запрос). Для учебных очков это допустимо, но результат не является доказательством знаний.
- Пока есть только JavaScript-задания. Для TypeScript потребуется транспиляция в браузере, для SQL — WebAssembly-база (DuckDB или sql.js).
- Монако подгружается с CDN jsDelivr (версия закреплена). Если CDN недоступен, включается простой редактор. При желании его можно разместить на своём домене.
- XP показывается после решения, но не хранится в базе (нет колонки): при необходимости считаем из решённых заданий.
- Один файл на задание (`solution.js`); выбор нескольких файлов — следующий этап.
- Наскрізні проекты в портфолио.
